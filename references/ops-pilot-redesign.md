# Ops Pilot：五种现象的重构配方

这份文档使用脱敏业务描述，不提交真实截图、内部域名、账户或工单材料。它是页面重构建议，不代表已修改线上 Ops Pilot。

## 1. 完成页重复证明成功

现象：申请概况、流程已结束、每个步骤已完成、申请完成、Market 完成、100% 进度反复占据首屏，交付结果在下方。

做法：合并为准确的完成结论；立即展示实际环境与交付物；审批/交付历史保留完整入口；正常完成只行内用绿。不能删去最终配置、凭据入口的权限边界或关键审计记录。

## 2. 交付页同时有多个进度体系

现象：服务交付完成、1/1、满格进度、步骤、统计条、验证 4/4 互相竞争。

做法：分别表达执行结果、校验结果、验收状态；交付物为主表面，证据按行展开，普通日志次级显示。当前任务若是确认交付，标题应说明等待谁确认；不能只写成功。

## 3. Manager 审核被长技术名称主导

做法：业务动作为标题，例如“新增 Kafka Topic”；技术名称为可复制次级标识；申请原因、影响环境、关键规格、SRE 结论与审批依据按任务排序。单资源规格采用分组事实，多个同类资源比较再使用表格。

## 4. SRE 历史审核被禁用表单和蓝提示占满

做法：历史模式一条提示；只读属性不使用 disabled Input/Select；显示当时的方案、审批依据和处理结果；当前任务入口保持明确。把“第 N 版”从标题前移走不等于删除版本：审计依据仍有稳定的快照标识。

## 5. 多环境申请使用多层卡片和两个空状态

做法：步骤头精简；只有一个环境导航；资源类型和实例合并为分组列表；右侧真实编辑区占主要宽度；无资源时只有一次“添加资源”行动。配置填写完成不等于已交付。

## 不新增的伪需求

不凭空添加“无负责人、推测关联、数据延迟、环境不完整”等开发诊断标签；它们只有在真实业务明确要求、数据存在且最终用户能行动时才可显示。手动维护的关系台账不自动变成新鲜度监控产品。示例数据必须标为示例，不能伪装线上结论。
